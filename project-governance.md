# Project Governance (Project-Level Progress + Task Integration)

This template repo now includes a **project-level governance layer** that aggregates progress across tasks while keeping the existing `dev-docs/**` task execution workflow intact.

## What Changed

### New project contract + entrypoint
- `.ai/project/CONTRACT.md`
  - Defines the sources of truth (SoT), enums, scanning rules, and lint/sync policies.
- `.ai/project/AGENTS.md`
  - AI entrypoint and operational commands for project governance.

### New skills (SSOT)
- `.ai/skills/workflows/planning/project-orchestrator/`
  - Front door for intake/triage/dedupe/mapping decisions (no product code changes).
- `.ai/skills/workflows/planning/project-sync-lint/`
  - Repo governance workflow for init/lint/sync.

### New repo tool (dependency-free Node ESM)
- `.ai/scripts/projectctl.mjs`
  - `init`: create `.ai/project/<project>/` from templates (idempotent by default)
  - `lint`: validate contract invariants, scan multi-root `dev-docs`, detect drift
  - `sync`: allocate missing `T-xxx` IDs, upsert registry tasks, regenerate derived views

### CI templates are now “governance-aware”
The templates copied by `node .ai/scripts/cictl.mjs init --provider <github|gitlab>` now include a governance lint job/step:
- `.ai/skills/testing/test-ci-github-actions/reference/templates/github-actions/ci.yml`
- `.ai/skills/testing/test-ci-gitlab-ci/reference/templates/gitlab-ci/.gitlab-ci.yml`

### dev-docs template alignment
The dev-docs bundle template now uses a **single-value** status:
- `.ai/skills/workflows/dev-docs/create-dev-docs-plan/templates/00-overview.md` uses `- State: planned`

Routing was updated to make the governance entrypoint discoverable:
- `AGENTS.md` includes `.ai/project/AGENTS.md`
- `.ai/AGENTS.md` includes `.ai/project/AGENTS.md`

## Operating Model (SoT + Automated Maintenance Chain)

### Sources of truth (no circular writes)
- **Task progress SoT:** `dev-docs/**/active/<task>/00-overview.md`
  - Under `## Status` there MUST be: `- State: planned|in-progress|blocked|done` (single value).
- **Task identity SoT:** `dev-docs/**/active/<task>/.ai-task.yaml`
  - `task_id` is authoritative (`T-xxx`).
  - `status` is allowed but treated as **derived display** (not authoritative for progress).
- **Project semantic SoT:** `.ai/project/<project>/registry.yaml`
  - Milestones/Features/Requirements + mappings.
  - `project.task_doc_roots` config (supports multi-root `dev-docs`).
- **Derived views (non-SoT):**
  - `.ai/project/<project>/dashboard.md`
  - `.ai/project/<project>/feature-map.md`
  - `.ai/project/<project>/task-index.md`
  - AUTO sections are regenerated by `projectctl sync`.

### LLM-first workflow (typical)
1. Intake/triage:
   - Use `project-orchestrator`.
2. Create a task bundle (execution layer):
   - Use `create-dev-docs-plan` to create `dev-docs/active/<slug>/...`.
3. Execution/progress updates:
   - Update `dev-docs/active/<slug>/00-overview.md` `- State: ...`
   - Humans only “check the boxes” under `## Acceptance criteria ...` during verification.
4. Sync project hub:
   - `node .ai/scripts/projectctl.mjs sync --apply --project main`
5. CI gate (project metadata drift):
   - `node .ai/scripts/projectctl.mjs lint --check --project main`

## Systemic Review (LLM Developer Perspective)

### Ripple effects and integration points
- dev-docs workflows:
  - `create-dev-docs-plan` template was updated to produce a contract-compliant `State:` line (`planned` single value).
  - Existing `dev-docs/**` execution patterns remain unchanged; governance reads bundle state but does not change bundle content.
- `plan-maker`:
  - `plan-maker` continues to write `roadmap.md` under `dev-docs/active/<task>/` and can be used as planning input for governance mapping.
  - `projectctl` currently does not parse `roadmap.md`; progress remains anchored in `00-overview.md`.
- `init/` pipeline:
  - The initialization pipeline explicitly avoids creating `dev-docs` bundles. That rule remains compatible with project governance because hub initialization is an explicit `projectctl init` action.
- CI + `cictl.mjs`:
  - Governance lint runs via the CI templates copied by `cictl.mjs`.
  - Lint is warning-only when the project hub is missing; real repos should run `projectctl init` once to enable strict consistency checks.

### Path references and discoverability
- Entry routing now explicitly points to `.ai/project/AGENTS.md` from both `AGENTS.md` and `.ai/AGENTS.md`.
- `create-dev-docs-plan` examples and templates are aligned to `dev-docs/` paths.

### Semantic alignment and conflict avoidance
- Progress is updated where execution happens (`dev-docs/**`), preventing “meta-only progress updates”.
- `.ai-task.yaml` is the identity anchor; `projectctl sync` mirrors status for convenience and lints “meta status ahead” as a warning.
- `State:` single-value rule prevents ambiguity and enables reliable parsing.

### Blocking points and failure modes
- **Hub not initialized:** `projectctl lint` emits a warning (exit 0). Real repos must run `projectctl init` once.
- **YAML format constraints:** `registry.yaml` must stay within a simple YAML subset (maps/lists/scalars). YAML anchors, multi-document YAML, and complex multiline scalars are not supported.
- **Missing/invalid task bundle status:** tasks without `00-overview.md` or without `- State:` generate warnings; `sync` falls back to `planned`.
- **Invalid meta YAML:** `sync` currently warns and does not auto-repair invalid `.ai-task.yaml` (future improvement).
- **Slug conflicts across roots:** `lint` errors if the same slug appears in multiple roots with different task IDs (prevents semantic drift).

### Known limitations / gaps (relative to a “fully automated” PM system)
- `projectctl sync` does not append semantic events to `changelog.md` (manual via `project-orchestrator`).
- `projectctl` does not provide a `query`/`search` command; natural-language “find related tasks” relies on the LLM reading `registry.yaml` and `dev-docs/**`.
- `registry.yaml` is rewritten by `sync` (comments/formatting are not preserved). Treat `registry.yaml` as machine-managed/LLM-managed SSOT.

## Requirement Coverage Assessment (Project-Level Progress Governance)

### Fully covered (with the current toolchain)
- **Macro progress aggregation:** derived views show status counts and task lists (`dashboard.md`, `task-index.md`).
- **Traceability structure:** `registry.yaml` supports Milestone/Feature/Requirement/Task relationships; tasks are always registered with `dev_docs_path` and status.
- **Multi-root dev-docs scanning:** config-first + auto-discovery fallback is implemented.
- **Migration policy:** missing `.ai-task.yaml` is a warning; meta files that exist are validated strictly.
- **CI integration:** governance lint runs in CI templates copied by `cictl.mjs`.

### Partially covered (requires LLM/operator conventions)
- **Natural-language intake → mapping:** covered by `project-orchestrator` skill, but there is no dedicated CLI query/search tool.
- **Live documentation protocol:** `sync` regenerates derived views and updates `registry.yaml`, but `changelog.md` updates remain manual.
